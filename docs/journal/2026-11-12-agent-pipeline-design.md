# 에이전트 파이프라인 설계: 기억은 파일에, 모드는 명령어로
- 날짜: 2026-11-12 / 관련: docs/11, D-23

## 배경
Orca로 작업하면서 "메인 에이전트가 서비스 내용을 전부 기억하고 서브 에이전트에게 일을 시키고, 다음 에이전트가 Jira를 관리하고, 또 다른 에이전트가 PR을 올리는" 파이프라인을 구상했다.

## 고려한 선택지
| 구상 | 판단 | 이유 |
|---|---|---|
| 메인 에이전트가 모든 것을 기억 | 그대로는 불가 | 세션은 맥락 한계가 있고 종료 시 기억이 사라짐 → 기억을 파일(STATUS, ADR, lessons, Jira)로 외부화 |
| 메인 → 구현 서브 에이전트 | 채택 | Orca의 조율자-작업자 구조와 일치 |
| Jira 전담 에이전트 | 대체 | 상태 전환은 판단이 필요 없는 일 → GitHub for Jira + 자동화 규칙 |
| PR 전담 에이전트 | 대체 | PR 설명은 구현자가 가장 잘 씀, 넘기면 맥락 손실 |
| (추가) 독립 검증 에이전트 | 채택 | 구현하지 않은 새 세션이 수용 기준을 대조해야 맹점이 줄어듦 |

## 결정과 이유
작업 성격에 따라 모드를 바꾼다.
- A 순차형: 기반 작업
- B 비교형: 인터랙션 작업. 시안 2개를 실기기로 비교해 선택. 라운드 최대 2회
- C 조율 + 구현 + 검증: 방향이 정해진 뒤 병렬 구현
- D 완전 자동(라벨 → GitHub Actions → PR): API 비용 때문에 보류(D-23)

비교형에서 둘 다 마음에 들지 않을 때를 위해 사람이 직접 전환하는 명령어(`/lunea-pick`, `/lunea-retry`, `/lunea-refine`, `/lunea-back-to-design`)를 만들고, 현재 모드는 Jira 라벨과 STATUS.md에 남겨 세션이 바뀌어도 유지되게 했다.
