# Git 흐름 정하기: main은 배포, dev는 통합
- 날짜: 2026-11-13 / 관련: D-26, docs/11 §5a

## 배경
PR #1~#5는 모두 `main`으로 바로 머지했다. 애플리케이션 코드(FND-02)를 쓰기 시작하면 "배포된 코드"와 "개발 중인 코드"를 나눠야 한다. 제품 책임자가 "main은 배포만 올라가야 한다"고 제안했다. 같은 날 저장소를 공개로 바꿔서 브랜치 보호도 무료로 쓸 수 있게 됐다.

## 고려한 선택지
| 결정 항목 | 선택지 | 장점 | 단점 |
|---|---|---|---|
| 기본 브랜치 | `dev`를 기본 / `main` 유지 | `dev`: PR·worktree가 자동으로 `dev`를 바라봐 에이전트 실수가 줄어듦 | `dev`: 저장소 첫 화면이 배포 코드가 아님 |
| 머지 방식 | 작업→`dev` 스쿼시 + `dev`→`main` 머지 커밋 / 모두 머지 커밋 / 모두 스쿼시 | 혼합: `dev`는 작업당 커밋 1개, `main`은 릴리스 단위 기록 | 모두 스쿼시: `dev`·`main` 기록이 어긋나 다음 릴리스에서 충돌 위험 |
| Jira 완료 시점 | `dev` 머지 / `main` 릴리스 | `dev`: 기존 자동화 규칙 그대로 사용 | `main`: "배포 대기" 상태와 별도 규칙 필요 |

전체 Git Flow(release 브랜치 등)는 혼자 개발하는 현 단계에 비해 무거워서 제외했다.

## 결정과 이유
세 항목 모두 위 표의 첫 번째 선택지(권장안)를 제품 책임자가 골랐다. 핵심은 **에이전트가 실수로 배포 브랜치를 건드릴 수 없게 하는 것**이다. 기본 브랜치를 `dev`로 두고, 규칙(CLAUDE.md, skills)과 저장소 설정(Rulesets)을 함께 둔다.

## 진행 중 생긴 문제와 대응
- CodeRabbit은 `main`으로 가는 PR만 리뷰하도록 설정돼 있었고, CI는 `main` push에서만 돌았다. 둘 다 `dev`를 추가했다.
- 기본 브랜치 변경과 Rulesets는 클라우드 세션 권한 밖이라 제품 책임자 단계로 분리했다(L-001).
